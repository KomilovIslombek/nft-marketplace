# Key decisions (and why)

Short answers to "why did you build it this way?", the questions an
interviewer or code reviewer is likely to ask. Each entry says what was
decided, why, and what it costs.

## 1. No fake data on screen

**Decision:** every number, name and section on the site comes from the
database. Where a feature doesn't exist, the UI says so instead of
pretending.

**Why:** the Figma template came with invented content: "240k+ artists", a
"Trending Collection" with a "1025+" badge, an auction countdown, a
newsletter form. Shipping that would mean the portfolio claims features the
code doesn't have. Concretely:

- Hero stats come from `GET /api/stats`. The "Auctions" label became
  "NFTs", because the app has no auctions.
- "Trending Collection" became **Top Categories**. There is no Collection
  model, so instead of inventing one, the section ranks the grouping the
  data really has (an NFT's category) by real sales volume, and keeps the
  Figma card design.
- The "Auction" banner became a **Spotlight** on the most traded NFT, with
  its real sale count and volume. The countdown was counting down to a
  date that had already passed.
- The newsletter form and "Connect Wallet" stay clickable, but they say
  plainly that they aren't connected. The newsletter form used to put the
  visitor's email into the URL.
- Controls that did nothing (the Marketplace "Collections" tab with its
  hardcoded "67", social icons linking nowhere) were removed.

**Cost:** the homepage numbers are small (18 NFTs, 11 artists), and that's
the honest figure. The demo history is generated by `npm run seed` from a
fixed random seed. The README says so: demo content, real mechanism.

## 2. Two new read endpoints instead of two new models

**Decision:** `GET /api/trending/nfts` and `GET /api/trending/categories`
are MongoDB aggregations over the existing `Sale` collection. No
`Collection` or `Auction` model was added.

**Why:** a model nobody can write to (there is no create-collection or
bidding flow) would just be another way to show seeded data. The `Sale`
documents are already the source of truth for Rankings, so trending is
built from the same data and the pages can't disagree. The `?period=`
windows live in `utils/periods.js`, shared with Rankings.

**Detail worth knowing:** the category previews use `$topN`, not
`$push` after a `$sort`. Only `$topN` guarantees the order inside a group.

## 3. Auth: JWT in an httpOnly, SameSite=Strict cookie

**Decision:** the token is never visible to JavaScript (`httpOnly`), is
only sent to the same site (`SameSite=Strict`), and requires HTTPS in
production (`Secure`).

**Why:** a token in `localStorage` can be stolen by any XSS bug.
`SameSite=Strict` blocks CSRF without a separate CSRF token. Login errors
use one message for "unknown email" and "wrong password", so the form
doesn't reveal which emails are registered (there is a test for that).

## 4. Hosting: Netlify (front) + Render (API) + Atlas, with a proxy

**Decision:** static frontend on Netlify, Express API on Render's free
tier, MongoDB Atlas M0. Netlify proxies `/api/*` to Render.

**Why the split:** static pages load instantly from a CDN even while the
free API server is asleep. The API needs a long-running Node process, which
Render provides without rewriting Express into serverless functions.

**Why the proxy:** without it the browser would call `onrender.com` from a
`netlify.app` page. That makes the auth cookie third-party: never sent
with `SameSite=Strict`, and blocked by Safari and Firefox. Through the proxy
everything is one origin, so the cookie is first-party, no CORS preflights
are needed, and the strict cookie settings can stay.

**Cost:** Render's free service sleeps after 15 idle minutes and takes up to
a minute to wake, and Netlify's proxy times out after about 26 seconds. The
frontend's `apiFetch()` retries read-only requests (never POSTs, which
might have gone through already) and shows a "waking up" note. A keep-alive
ping is optional. See [DEPLOYMENT.md](DEPLOYMENT.md).

## 5. One frontend config instead of nine hardcoded URLs

**Decision:** `front/assets/js/config.js` sets `API_BASE` once. Locally it
uses the same hostname on port 5000; in production it uses a relative
`/api`.

**Why "same hostname":** `127.0.0.1` and `localhost` are different sites as
far as cookies are concerned. A page on `localhost:5500` calling
`127.0.0.1:5000` would never get its `SameSite=Strict` cookie back.

## 6. Tests: node:test + supertest + an in-memory MongoDB

**Decision:** 35 integration tests run the real Express app (`app.js`)
against a real `mongod` started in memory by `mongodb-memory-server`.

**Why integration rather than unit tests:** most of the logic that can go
wrong lives in Mongoose queries and aggregation pipelines (period windows,
crediting resales to the creator, float rounding). Mocking the database
would test the mocks. **Why `node:test`:** it ships with Node 20+, so it's
one less dependency, and Mongoose's documentation warns about Jest's
default environment. **Why `app.js` is separate from `server.js`:** tests
need the app without connecting to the real database or opening a port.

CI runs the suite on every push (GitHub Actions). It needs no secrets,
because the database is in memory.

## 7. Demo accounts can't be logged into

**Decision:** `npm run seed` gives demo creators a random password on every
run (unless `DEMO_PASSWORD` is set locally).

**Why:** the seed script is in a public repo. A fixed password there would
let anyone sign in as a demo creator on the live site and delete the demo
NFTs.

## 8. User content is rendered with textContent, never innerHTML

NFT titles and usernames are user-submitted. Every card is built as DOM
nodes with `.textContent`, so a title like `<img onerror=…>` is shown as
text instead of running. Search input is regex-escaped before it reaches
MongoDB, so `.*` is a literal search, not "match everything" (there is a
test for this too).

## 9. Links carry ids in `#fragments`, not `?query` strings

`nft.html#id=…`, `marketplace.html#category=Art`, `rankings.html#period=all`.
The local static server (`serve`) redirects `page.html` to `page` and drops
the query string on the way. A fragment never reaches the server, so it
survives any redirect on any host.
